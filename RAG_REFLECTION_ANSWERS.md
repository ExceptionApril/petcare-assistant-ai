# RAG System Reflection Essay

Chunking documents is essential for local RAG systems. A 1,000-page document contains 300,000 to 500,000 tokens, but models like my llama3.2:1b only support 2,000 to 4,000 tokens. Without chunking, memory usage explodes as the system loads entire documents into RAM, overwhelming CPU and causing unacceptable latency. Chunking solves this by breaking documents into 512 to 1,024 token pieces, storing them in a vector database, and retrieving only semantically relevant chunks during queries. This keeps memory reasonable, maintains fast response times, and improves answer quality because the LLM works with focused context. My implementation uses LlamaIndex's SimpleDirectoryReader with VectorStoreIndex and HuggingFace embeddings to automate this process. Chunking is the core reason local RAG systems work efficiently on consumer hardware.

In my system, the Retriever and Generator serve distinct roles. The Retriever searches the vector database to find chunks matching user questions. It converts queries to embeddings using HuggingFace, performs semantic search, and returns the top 3 to 5 results. The Generator is the LLM—Ollama running llama3.2—which takes retrieved chunks and generates coherent answers. This separation enables effective debugging. If retrieved chunks are irrelevant but the LLM outputs correct text, the Retriever failed: embeddings might be broken, indexing flawed, or semantic similarity miscalibrated. I would verify the embedding model, chunking strategy, and vector search quality. Conversely, if the Retriever returns good chunks but the Generator produces nonsensical answers, the LLM is failing. In my codebase, `VectorStoreIndex` performs retrieval and `Ollama` is the generator, allowing independent testing of each component.

Local deployment over cloud APIs makes sense for several reasons. Cloud APIs charge per token, so high-volume queries accumulate significant costs, while local systems require only one-time hardware investment. Local systems also provide instant queries without internet dependency or rate limits, ensuring reliability. Privacy is critical—pet care data remains on your servers, never sent to external APIs. The trade-off is managing hardware, RAM, and CPU yourself. My 1B model has minimal overhead but slower inference than GPT-4. Responses take seconds rather than milliseconds, which is acceptable for informational lookups. You must maintain the system, update models, and manage the database. However, for smaller organizations with privacy requirements and acceptable latency, local deployment wins. I chose this approach for control, cost efficiency, and independence from external services.
